# 日志设计

本文是日志组件的统一设计，覆盖过程日志中间件、kv 过程数据、全局 logger 与配置。实现以此为准；术语定义见 `CONTEXT.md` 与 `backend/CONTEXT.md`，

## 目标与非目标

**目标**

- 一次 HTTP 请求处理结束时，由中间件输出**一行**过程日志（单行请求摘要），聚合请求基础字段与业务过程数据。
- 业务过程数据以 kv 形式放入请求 `context.Context`，任何分层（application/domain/infrastructure）都能追加，无需依赖 gin。
- 全服务共用一个 logger：启动、停机、请求摘要、错误输出风格一致，预留 ELK/Loki 消费。

**非目标**

- 请求中途的事件流日志（每个业务步骤独立成行）——如日后需要，在本方案上补一个显式事件 API 即可，摘要机制不受影响。
- 日志落盘与轮转：输出到 stdout，由容器/平台收集。
- 敏感键过滤：**明确不做**（用户决策，2026-09-23）。防护依赖团队约定：不把密码、令牌明文放进过程数据。此决策的风险由约定承担，组件不设防。

## 组件结构

新增 `backend/internal/kernel/applog` 包（横切组件统一安置于 `internal/kernel/`)）：

```go
// Init 按配置初始化全局 logger；进程生命周期调用一次，未调用时 L() 返回 NOP logger。
func Init(cfg Config)

// L 返回全局 logger。
func L() *zap.Logger

// NewCollector 返回携带过程数据收集器的子 context；请求结束由中间件统一输出。
func NewCollector(ctx context.Context) context.Context

// Add 向当前请求的过程数据追加一条 kv。
func Add(ctx context.Context, key string, value KVer)

// Fields 返回当前请求已收集的过程数据快照；仅供过程日志中间件合并输出。
func Fields(ctx context.Context) map[string]any
```

- zap 原生接入，`L()` 返回 `*zap.Logger`，不包接口。
- 编码与级别由配置文件控制：`log.format: text|json`（默认 `json`）、`log.level: debug|info|warn|error`（默认 `info`）。生产 JSON、本地 text。
- 输出目标 stdout；`Init` 需保证未调用时 `L()` 可安全使用（NOP），测试零配置。

### 分层边界

- `applog` 是无业务语义的基础组件，application/domain 层可依赖它（不构成依赖基础设施）。
- presentation 层中间件负责：生成请求标识、挂收集器、请求结束时输出摘要行。
- 过程数据经 `c.Request.Context()` 流入 application 层（现状已如此），业务代码在任意深度 `applog.Add(ctx, ...)` 追加。

## 过程数据（kv）

### 值类型

受限类型集，编译期拒绝其他类型：

```go
type KVer interface{ logKV() }

String(string) / Int64(int64) / Float64(float64) / Bool(bool) / Time(time.Time) / Err(error)
```

调用形式：`applog.Add(ctx, "wrong_count", applog.Int64(3))`。对象、切片等复杂值不收；确需记录时调用方自行转成上述基本类型，保证输出可预测。

### 键规范

- 键用英文小写 snake_case（如 `wrong_count`、`ai_usage`），便于 ELK/Loki 检索；禁止中文键。
- **保留键**（中间件自动写入，业务键不得占用，Add 命中时静默丢弃并 debug 记录）：

| 保留键 | 含义 |
|---|---|
| `request_id` | 请求标识 |
| `method` | HTTP 方法 |
| `path` | 请求路径 |
| `status` | 响应状态码 |
| `latency_ms` | 耗时（毫秒） |
| `client_ip` | 客户端 IP |
| `user_id` | 已认证用户 ID（未认证时整个字段省略，zap 无 int64 空值语义） |
| `error` | 处理错误信息 |

## 中间件行为

替换 `gin.Default()` 为 `gin.New()` + 本中间件 + zap 版 Recovery。每请求：

1. 生成短随机请求标识（如 16 hex 字符），写入响应头 `X-Request-Id` 回显给客户端。
2. `ctx := applog.NewCollector(c.Request.Context())`，`c.Request = c.Request.WithContext(ctx)`。
3. `c.Next()` 返回后输出单行摘要：保留键全部字段 + ctx 累积的业务 kv。
4. 级别映射：2xx/3xx → Info，4xx → Warn，5xx → Error。告警规则可直接挂 `level` 字段。
5. `/healthz` 探针不记录（避免周期性噪音与日志量翻倍）。

请求标识由服务端自生成，不读取上游传入（无网关/链路追踪前提；将来接网关时再评估透传）。

## 全服务统一

- `main` 中启动、监听、DB 失败、优雅停机等日志全部改走 applog；`log.Fatalf` 换成 logger Fatal（zap Fatal 后自动 `os.Exit(1)`）。
- stdlib `log` 从服务代码退场。

## 配置

全部配置迁入 `config.yaml`，形如：

```yaml
addr: 127.0.0.1:8080
mysql_dsn: root:@tcp(127.0.0.1:3306)/go_clean_template?charset=utf8mb4&parseTime=true&loc=Local
jwt_secret: <必填，启动时校验>
access_ttl: 30m
refresh_ttl: 720h
log:
  format: json   # text | json，缺省 json
  level: info    # debug | info | warn | error，缺省 info
```

## 实现勘误（2026-09-23 实现后回写）

- `user_id` 未认证时的行为如保留键表所述：字段省略而非空值。
- `config` 包加载失败（文件解析失败、缺 `jwt_secret`）仍走 stdlib `log.Fatalf`：此时 logger 配置本身尚未加载，属鸡生蛋边界，不强行接入 applog。
- panic 恢复用自写 `zapRecovery`（zap 字段输出堆栈），非 zap 官方 adapter；中间件顺序 processLog → zapRecovery，保证 panic 请求也有摘要行。
- `applog.Fields` 为实现新增的公共 API（中间件跨包读取快照），已补进上文组件结构。

## 验证方式

- 单测：kv 收集器（类型集、保留键拒绝）、级别映射（按状态码）。
- 冒烟：本地起服务，text 格式观察请求摘要行、`X-Request-Id` 响应头、`/healthz` 无日志。
